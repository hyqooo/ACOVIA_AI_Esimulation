# 反証条件ウォッチ

「やめる数字」と判定期限を登録し、期限が来たら知らせる。

## なぜ必要か

12本のシミュレーションで、反証条件を数字で先に決めた案（I・J・L）は成功し、**決めなかったK だけが失敗した。**

Kでは `vc-review/` が2027年に「何%を下回ったら何をやめるのか、今書け」と要求し、`ceo-cpo/` が保留した。**その要求を飲む実行コストは、その日の会議10分だった。**

## このツールがやること（2つだけ）

1. **判定期限が来たことを、忘れる前に知らせる**（学び2：判定期限を日付で切る）
2. **条件を後から変えたことを、見えるようにする**（学び7：撤退条件は開始日に決める）

**2つ目が本体。** 条件は「破られること」より「静かに書き換えられること」で死ぬ。このツールは変更を禁止しない。**理由と変更前の文言を必ず記録に残すだけ。**

## 使い方

```bash
cp conditions.sample.json conditions.json   # R-1〜R-9・L-1 が入っている

node conditions.mjs list                     # 一覧
node conditions.mjs check                    # 判定期限が来ているもの（未判定があれば exit 1）
node conditions.mjs judge R-3 --result=cleared --value=31.2% --note="転換率31.2%"
node conditions.mjs judge R-5 --result=triggered --value="984,739円 < 1,140,000円"
node conditions.mjs amend R-2 --to="..." --reason="基準の穴の是正。緩和ではない" --who=代表1
node conditions.mjs history                  # 判定と変更の履歴
```

`check` は未判定があると **exit 1** を返すので、cron や CI に置ける。

```bash
# 毎朝
0 9 * * * cd /path/to/condition-watch && node conditions.mjs check
```

## 条件の書き方

```json
{
  "id": "R-3",
  "condition": "「はじめの15分」→「決めどき45分」の転換率が15%未満",
  "onTrigger": "「はじめの15分」を停止する",
  "owner": "代表3",
  "judgeOn": ["2027-12-31"],
  "decidedOn": "2026-08-01"
}
```

- `condition` は**数字を入れる。** 「うまくいかなければ」は条件ではない
- `onTrigger` は**やめること・止めることを具体的に書く。** 「見直す」は行動ではない
- `judgeOn` は**日付の配列。** 常時監視なら `"every": "month"`
- 4つとも必須。1つでも欠けると読み込み時にエラーになる

## `history` が出す警告

判定が8回以上あって発動が0回のとき、こう出る。

> ⚠ 一度も発動していません。**それは良い経営の証拠かもしれないし、条件が緩い証拠かもしれません。**
> 反証条件の目的は撤退させることではなく、「間違っているかもしれない」と定期的に思い出すことです。
> 一度も殴られない条件は、その機能を果たしていません。引き直しを検討してください。

本命シナリオの `vc-review/` が第22回（2031年11月）で言ったことを、そのまま実装してある。

## データ

`conditions.json`（定義）と `judgments.jsonl`（追記のみの記録）。

**このリポジトリでは両方 `.gitignore` している。** `ACOVIA_AI_Esimulation` は公開リポジトリであり、実際の経営数字を置く場所ではないため。

**`hyqooo/hopecadi`（非公開）へ移したときは、`conditions.json` をコミットすることを推奨する。** 条件を変えたことが `git diff` に出るほうが、このツールの目的（変更を見えるようにする）に合う。`judgments.jsonl` は判定値そのものを含むので、扱いは運用側で決めること。
