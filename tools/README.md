# tools/｜本命シナリオを実際に回すための自前ツール

本命シナリオ（`../honmei/`）を運営文書として使うとき、**毎月・毎四半期に必ず発生する作業**のうち、機械化できるものをここに置く。

**すべて依存パッケージなしのNodeスクリプト（Node 18+）。** どちらも `hyqooo/hopecadi` 側に移してよい設計にしてある（このリポジトリはシミュレーションの記録であり、本来の置き場所ではない）。

---

## なぜこの2つを最初に作ったか

12本のシミュレーションを通して、**会社を救ったのはプロダクトではなかった。**

- 2029年に外部メディアの見出し（「不妊治療をやめる決断を後押しするサービス」）を差し替えさせた反証材料は、**6ヶ月後フォローの最後の1問の2年分の集計**だった
- 2031年に出資の打診を条件どおり断れたのは、**2026年8月1日に書いた1行**だった
- 12本で唯一の失敗判定だったKは、**反証条件を数字で書かなかった1本**だった

**どちらも数百行で作れて、どちらもプロダクトではない。** 逆にHUDのような道具は、本命シナリオの時間軸では2028〜2030年相当のものになる。準備の完成度と顧客価値の証明は別物である（失敗パターン12）。

| ツール | 何をするか | いつから要るか |
|---|---|---|
| [`followup-ledger/`](followup-ledger/) | 7日後フォローと6ヶ月後フォロー（＝逆方向の数字）の配信管理と集計 | **有償1件目から** |
| [`condition-watch/`](condition-watch/) | 反証条件の判定期限を知らせ、条件文の変更を記録に残す | **反証条件を決めた日から** |

## `hyqooo/hopecadi` との関係

現実側ではすでに、セッション中のサポーター支援ツール（`zoom-relay` / `classifier` / `hud-prototype`）が開発されている。**設計判断は本命シナリオと一致している**（自由生成させない／危機対応をAIに判定させない／逐語を言い換えない）。

本命シナリオ側の記述「AIをセッション本体に入れない」は、この実態に合わせて **`honmei/00-overview.md` §7-2** に書き直した。守る線は「セッション中かどうか」ではなく、**①相談者に触れるか ②判断を人間から取り上げるか** の2つである。

**HOPE CADIの見本フレーズは「前半15分（整理しない時間）」側の資産である。** 本命シナリオの「後半30分（4つの箱・再検討条件・次の一歩の主語）」側のカテゴリと見本は、まだ存在しない。本命シナリオを採るなら、そこがclassifierの次の開発対象になる。
